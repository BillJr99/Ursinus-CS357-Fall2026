## About This Tutorial

Every framework is a wager: *we think these patterns repeat often enough to justify hiding them.*  When the wager pays off, you write a research agent in twenty lines instead of two hundred.  When it doesn't, you spend an afternoon fighting the framework's assumptions instead of building your system.  This tutorial examines what the major 2024-2025 agent frameworks actually hide, what they cost you when they get it wrong, and how to decide which level of abstraction belongs in which project.  Today's path runs **why frameworks exist → the leaky abstraction problem → framework comparison → choosing the right tool → hands-on: a LangChain agent on Ollama → raising the ceiling: a deep agent → Pydantic AI and the context window**.

## Key Concepts

| Term | Plain-English Definition | Where You'll Meet It |
|---|---|---|
| Abstraction | Hiding complexity behind a simpler interface: you use a high-level concept (like "Agent") without thinking about all the HTTP calls, prompt formatting, and response parsing underneath. | CrewAI's `Agent(role="Researcher", goal="...")` hides the system prompt construction, LLM call, tool routing, and memory management that raw SDK code would require explicitly. |
| Leaky Abstraction | An abstraction that fails to hide its underlying complexity at inconvenient moments: you must understand the hidden layer to fix the problem. | When LangGraph's state graph puts unexpected content into the context of an agent, you need to understand how LCEL (LangChain Expression Language) formats prompts to debug it. |
| LangGraph | A graph-based agent framework from LangChain (`pip install langgraph`) that models multi-agent workflows as a state machine: nodes are agents or processing steps, edges are transitions, and state is a shared data object passed between nodes. | A three-agent pipeline (Researcher -> Drafter -> Critic) becomes a directed graph with conditional edges for revision loops. |
| CrewAI | A high-level framework (`pip install crewai`) for building teams of role-based agents. The three core concepts are Agent (a role with a goal), Task (a unit of work assigned to an agent), and Crew (the team of agents and the process that coordinates them). | `Crew(agents=[researcher, drafter, critic], tasks=[...], process=Process.sequential)` runs all tasks in order without writing any routing logic. |
| AutoGen | A conversational multi-agent framework from Microsoft Research (`pip install pyautogen`) where agents communicate by sending messages to each other and can execute code. The `GroupChat` pattern routes messages between multiple agents based on a manager's decisions. | A `UserProxyAgent` can run Python code generated by an `AssistantAgent` and report the output back, enabling a coding feedback loop. |
| Agno | A lightweight, low-ceremony framework (`pip install agno`) focused on clean tool and memory APIs with minimal framework overhead. Previously called Phi Data. | `Agent(model=Ollama(id="llama3.1:8b"), tools=[DuckDuckGo()], memory=...)`, a three-line agent definition with tool use and memory. |
| Pydantic AI | A typed agent framework (`pip install pydantic-ai-slim`) from the team behind the Pydantic validation library. An `Agent` holds a model, instructions, and tools, and runs the tool-calling loop for you; hooks let you inspect every request before it is sent. | Part V builds one agent step by step (memory, a skill, a tool, an MCP server, the loop) and prints the context window after each step. |
| DeepAgents | A high-level harness from LangChain (`pip install deepagents`) built *on top of* LangGraph that ships an entire agent architecture pre-built: a **planning/todo tool**, spawnable **sub-agents with isolated context windows**, a **virtual filesystem** for offloading long context to disk, and a detailed built-in system prompt (modeled on Claude Code). | `create_deep_agent(model="ollama:llama3.2", tools=[search], system_prompt="...")`, a research agent that plans its own steps, delegates sub-tasks, and writes intermediate notes to files, all without you writing a loop. |

# Part I: Why Frameworks Exist

In this part, you will compare the major agent frameworks side-by-side and identify what each one hides from the developer.  The goal is to build the intuition that a framework's convenience always costs you visibility into what is happening underneath.

## Framework Comparison

Every agent system, regardless of framework, must solve the same four boilerplate problems: **memory management** (which prior turns does the agent see?), **tool routing** (how does the model's function-call land in real code?), **prompt templating** (how do dynamic values get inserted without string bugs?), and **conversation history** (how is the message list accumulated and truncated?).  Frameworks pre-solve these so you don't re-solve them on every project.  The cost is **abstraction leakage**: the moment the framework's assumptions diverge from your requirements, the hidden machinery starts working against you.

Choosing a framework is like choosing a car vs. a motorcycle vs. a bicycle for a commute.  Each has advantages at different scales and route types.  The mistake is choosing based on prestige rather than fit.

| Framework | Best For | Abstraction Level | Code Volume | Control Level | Key Concept | Install Command |
|---|---|---|---|---|---|---|
| LangChain / LangGraph | Complex pipelines with stateful branching, conditional loops, and monitoring via LangSmith | High (LCEL chain syntax, StateGraph API) | Verbose, LangGraph requires explicit node and edge definitions | Moderate: graph structure is explicit but prompt construction is often hidden | Chains, Runnables, StateGraph | `pip install langchain langgraph langsmith` |
| DeepAgents (built on LangGraph) | Long-horizon, open-ended tasks: deep research, multi-file coding, investigations that must plan their own steps, delegate sub-tasks, and manage context over many turns | Very high: hides the *entire* agent architecture (planning loop, sub-agent delegation, virtual filesystem, system prompt) on top of LangGraph | Very concise: a capable deep agent in ~5 lines | Low: an opinionated harness; the planning, delegation, and memory behavior are built in and hard to see | `create_deep_agent`, planning tool, sub-agents, virtual filesystem | `pip install deepagents` |
| CrewAI | Role-based agent teams; demos; educational contexts where agent "roles" map cleanly onto tasks | High (Crew/Task/Agent abstractions hide nearly all implementation) | Concise: a 3-agent crew in under 30 lines | Low-moderate: framework decides much of the prompt wording around your descriptions | Agent role, Task description, Crew process | `pip install crewai crewai-tools` |
| AutoGen | Conversational multi-agent systems; code execution feedback loops; agents that write and run code | Medium-high: GroupChat routing is abstract but agent system messages are explicit | Moderate: explicit agent definitions but automatic conversation routing | Moderate-high: agents are explicit but conversation flow is managed by the GroupChatManager | AssistantAgent, UserProxyAgent, GroupChat | `pip install pyautogen` |
| Agno (formerly Phi Data) | Lightweight single and multi-agent systems where you want clean APIs without framework overhead | Low-medium: thin wrapper around direct LLM calls with clean tool and memory APIs | Concise: minimal boilerplate | High: you control system prompts, tool schemas, and memory directly | Agent, Tool, Memory | `pip install agno` |
| smolagents (Hugging Face) | A first framework after a hand-written loop; small agents whose tools are plain Python functions | Low: a thin loop, and its `CodeAgent` writes Python code as its actions instead of JSON tool calls | Concise: an agent with one `@tool` in under ten lines | High: the loop is short enough to read, but a `CodeAgent` runs model-written code, so it needs a sandbox | `@tool`, `ToolCallingAgent`, `CodeAgent` | `pip install smolagents` |
| Pydantic AI | Typed single agents and small pipelines where you want to see each request; structured, validated output | Low-medium: a thin `Agent` over the provider API, with an inspectable loop (`agent.iter`) | Concise: a tool-using agent in about ten lines | High: you write the instructions and choose memory, skills, tools, and MCP servers; the framework handles schemas, parsing, and the loop | Agent, instructions, tools, toolsets, hooks | `pip install "pydantic-ai-slim[openai,mcp]"` |
| LlamaIndex | Retrieval-heavy systems, RAG pipelines, data connectors to external sources | Medium: query engine abstracts retrieval but tool use requires explicit wiring | Moderate | Moderate | Index, QueryEngine, Router | `pip install llama-index` |
| Raw OpenAI / Ollama SDK | Learning how agents work, maximum control, custom frameworks | None: you write everything explicitly | High: everything from scratch | Maximum: you decide every detail | Direct API calls | `pip install openai` or install Ollama from https://ollama.com |

# Part II: The Leaky Abstraction Problem

In this part, you will trace what each framework hides inside the same three-agent pipeline, and practice identifying the specific hidden mechanism that could leak and cause a bug, because the most common framework bugs require understanding the hidden layer to fix.

## 2.  What Frameworks Hide

When a framework's assumption breaks down, you must understand the hidden layer to fix the problem.  The same three-agent pipeline, implemented in three frameworks, hides different machinery in each one.

## The Same Pipeline, Three Frameworks

Consider a three-agent pipeline: **Researcher** (searches the web and retrieves relevant passages) -> **Drafter** (writes a response using those passages) -> **Critic** (identifies weaknesses and returns a revision list).  Below is the conceptual structure in three frameworks, with the hidden machinery surfaced.

The three code blocks below implement the same three-agent pipeline in three different frameworks.  As you read each one, note what you have to write explicitly versus what the framework handles invisibly; those invisible parts are exactly where abstraction leaks can occur.

**LangChain / LangGraph (`pip install langgraph`):**

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict

class PipelineState(TypedDict):
    question: str
    passages: list[str]
    draft: str
    revision_notes: str

graph = StateGraph(PipelineState)
graph.add_node("researcher", researcher_chain)  # LCEL: prompt | llm | parser
graph.add_node("drafter",    drafter_chain)
graph.add_node("critic",     critic_chain)
graph.add_edge("researcher", "drafter")

# Conditional edge: if revision needed, loop back to drafter; otherwise end
graph.add_conditional_edges("critic", should_revise, {"yes": "drafter", "no": END})
app = graph.compile()
result = app.invoke({"question": q})
```
*What this makes easy:* Stateful loops, conditional branching, streaming intermediate results to LangSmith for monitoring.  Every node's input and output is a typed dictionary slice of `PipelineState`.

*What this hides (and can leak):* The `PipelineState` accumulates state from all prior nodes.  If `researcher_chain` adds a key to the state, the `critic_chain` can see it, even if you didn't intend that.  LCEL's (LangChain Expression Language) `|` operator overloading hides the prompt structure; to see the exact system prompt your Researcher is receiving, you must call `researcher_chain.get_prompts()`.

---

The CrewAI version replaces explicit routing code with plain-English role descriptions.  Notice how much less Python you write, and think about what the framework is generating on your behalf that you cannot see.

**CrewAI (`pip install crewai crewai-tools`):**

```python
from crewai import Agent, Task, Crew, Process
from crewai_tools import SerperDevTool  # web search tool

researcher = Agent(role="Researcher",
                   goal="Find accurate and relevant passages for the question",
                   backstory="You are a rigorous academic researcher who finds primary sources.",
                   tools=[SerperDevTool()])
drafter    = Agent(role="Drafter",
                   goal="Write a clear, well-structured response using the passages",
                   backstory="You are a skilled technical writer.")
critic     = Agent(role="Critic",
                   goal="Identify logical gaps and unsupported claims in the draft",
                   backstory="You are a demanding editor who catches every weakness.")

task_r = Task(description="Research the following question: {question}",
              agent=researcher, expected_output="A list of 3-5 relevant passages with sources")
task_d = Task(description="Write a response using the research passages: {passages}",
              agent=drafter,    expected_output="A 3-paragraph response draft")
task_c = Task(description="Critique the following draft: {draft}",
              agent=critic,     expected_output="A bullet list of 3-5 revision notes")

crew = Crew(agents=[researcher, drafter, critic],
            tasks=[task_r, task_d, task_c],
            process=Process.sequential)
crew.kickoff(inputs={"question": q})
```
*What this makes easy:* Role semantics are human-readable: great for demos and for explaining agent behavior to non-technical stakeholders.  The `backstory`, `role`, and `goal` fields form the agent's identity in plain English.

*What this hides (and can leak):* CrewAI writes part of every agent's system prompt for you: the `role`, `backstory`, and `goal` are injected into a prompt template you cannot see by default.  Inter-task data passing is implicit: `{passages}` in `task_d` is filled by the output of `task_r` automatically.  If the Researcher's output doesn't match what the Drafter's description expects, the pipeline silently uses unexpected data.

The AutoGen version exposes the shared `groupchat.messages` list explicitly.  As you read it, ask yourself: which agents can see which messages, and could that sharing cause unintended behavior?

**AutoGen (`pip install pyautogen`):**

```python
import autogen

llm_config = {"model": "gpt-4o-mini", "api_key": "...", "temperature": 0}

researcher = autogen.AssistantAgent(
    "researcher",
    system_message="You search for and retrieve relevant passages on the given question.",
    llm_config=llm_config
)
drafter = autogen.AssistantAgent(
    "drafter",
    system_message="You write clear responses using passages provided to you.",
    llm_config=llm_config
)
critic = autogen.UserProxyAgent(
    "critic",
    human_input_mode="NEVER",  # fully automated
    code_execution_config=False,
    system_message="You identify weaknesses in drafts and return a revision list."
)

groupchat = autogen.GroupChat(
    agents=[researcher, drafter, critic],
    messages=[],
    max_round=6  # prevents infinite loops
)
manager = autogen.GroupChatManager(groupchat=groupchat, llm_config=llm_config)
researcher.initiate_chat(manager, message=q)
```
*What this makes easy:* Conversational handoffs between agents; code execution built in for the UserProxy pattern; native async support for parallel agent execution.

*What this hides (and can leak):* All three agents share the `groupchat.messages` list: every agent sees every message from every other agent in every round.  The GroupChatManager uses an LLM to decide which agent speaks next, which is itself a prompt injection surface.  If the Critic's feedback mentions something that contradicts the Researcher's retrieval, the Drafter may update its draft in a direction the developer did not intend.

> Many beginners assume that using a framework means they do not need to understand what the framework is doing: "it handles all of that."  In practice, **the most common LangChain, CrewAI, and AutoGen bugs require understanding the framework's hidden behavior** to fix: why is agent A seeing agent B's messages?  Why is the state carrying stale data from three turns ago?  Why is CrewAI sending a 3,000-token system prompt for a simple task?  You must understand the hidden layer to fix leaks.
{: .tb-pitfall data-title="Common Misconception"}

The three frameworks above hide the *plumbing* around a pipeline you still design.  One more level up sits **DeepAgents** (built on LangGraph), which hides the pipeline itself: the loop, the planning, and the delegation between sub-agents all move inside the framework.  Because it hides the most, it is the hardest to debug when it leaks; we examine it hands-on in Part IV once you have built the explicit loop it replaces.

In this part, you will apply a selection rubric to realistic project scenarios and practice justifying your framework choice against the strongest counterargument - the professional skill of arguing for a technical decision, not just making one.

## 3.  The Selection Decision

Choosing a framework before understanding the problem is like choosing a power tool before knowing what material you're cutting.  Different frameworks optimize for different primary use cases.

## Framework Selection Decision Table

| Scenario | Recommended Approach | Why | Fastest Way to Start |
|---|---|---|---|

# Part IV: Hands-On, Building with LangChain

## Hands-On, A LangChain Agent on Ollama

> **A note on versions:** LangChain's APIs evolve quickly; package names, import paths, and helper functions have all changed across releases and will change again.  The code below is pinned to *conceptual clarity*: the structure (a chat model object, a decorated tool, a bind-tools call, an explicit loop) is stable even when the spelling changes.  When something does not import, check the current documentation at https://python.langchain.com/docs/ rather than fighting the error message.

**Step 1: the model object.**  LangChain wraps every provider behind a common chat interface. `ChatOllama` is the wrapper for your local server (`pip install langchain-ollama`); its `.invoke()` is doing exactly what your Local Agent Lab `requests.post` to `/api/chat` did, with retry, parsing, and message formatting hidden inside:

```python

# pip install langchain-ollama langchain-core
from langchain_ollama import ChatOllama

llm = ChatOllama(model="llama3.2", temperature=0)
print(llm.invoke("In one sentence: what is an agent?").content)
```

**Step 2: a tool and an agent loop.**  The `@tool` decorator builds the JSON schema for you *from the function's type hints and docstring*, the same schema you wrote by hand in the Tool Use activity. `bind_tools` attaches the schemas to every request, and the loop below is deliberately written in the same shape as your Local Agent Lab loop so you can see what moved into the framework and what did not:

```python
from langchain_core.tools import tool
from langchain_core.messages import HumanMessage, ToolMessage

@tool
def days_between(start_iso: str, end_iso: str) -> str:
    """Returns the number of days between two ISO dates (YYYY-MM-DD)."""
    from datetime import date
    d0, d1 = date.fromisoformat(start_iso), date.fromisoformat(end_iso)
    return str((d1 - d0).days)

llm_with_tools = llm.bind_tools([days_between])
registry = {"days_between": days_between}   # still YOUR security boundary

messages = [HumanMessage("How many days between 2026-08-31 and 2026-12-07?")]
for _ in range(4):                          # perceive-plan-act, same as Local Agent Lab
    ai = llm_with_tools.invoke(messages)    # framework: HTTP, formatting, parsing
    messages.append(ai)
    if not ai.tool_calls:                   # yours: the stopping decision
        print(ai.content)
        break
    for call in ai.tool_calls:              # yours: execution and its gates
        result = registry[call["name"]].invoke(call["args"])
        print(f"[tool] {call['name']}({call['args']}) -> {result}")
        messages.append(ToolMessage(content=result, tool_call_id=call["id"]))
```

Read the comments as a ledger: the framework absorbed the *plumbing* (schema generation, request formatting, `tool_calls` parsing into typed objects), while the *authority* (which functions exist, when to stop, whether a call needs human confirmation) stayed in your loop.  LangChain also ships prebuilt agent loops (e.g., LangGraph's `create_react_agent`) that absorb the loop itself; use them once you can say precisely what they took from you.

**Step 3: a multi-agent handoff.**  Two "agents" are two differently-prompted model objects; the handoff is nothing more than one agent's output becoming the other agent's entire context:

```python
from langchain_core.messages import SystemMessage, HumanMessage

clarifier = ChatOllama(model="llama3.2", temperature=0)
executor  = ChatOllama(model="llama3.2", temperature=0.3)

question = "Summarize why local models matter."

# Agent 1: turn a vague request into a precise, self-contained brief
brief = clarifier.invoke([
    SystemMessage("You are a clarifier. Rewrite the user's request as a precise, "
                  "self-contained brief: audience, length, and three points to "
                  "cover. Output only the brief."),
    HumanMessage(question),
]).content

# The handoff: the executor's ENTIRE context is the clarifier's output
answer = executor.invoke([
    SystemMessage("You are an executor. Fulfill the brief exactly as written."),
    HumanMessage(brief),
]).content
print(answer)
```

Notice what the handoff pattern controls that a shared group chat does not: the executor sees *only* the brief, not the original question, not the clarifier's system prompt.  In LangGraph terms, this is a two-node graph whose state carries a single `brief` field; in Part II's terms, it is the leak-proof version of AutoGen's shared message list.

**The extended tutorial:** the course notebook [langchain_ollama_multiagent_tutorial.ipynb](https://www.billmongan.com/Ursinus-CS357-Fall2026/files/notebooks/langchain_ollama_multiagent_tutorial.ipynb) develops this sequence end to end: environment setup, a first raw query, the multiply tool with a single tool-call roundtrip, retrieval over a directory of documents (RAG), a supervisor pattern that exposes sub-agents as tools, and the clarifier -> executor handoff above, with exercises after each stage.

## Hands-On, Raising the Ceiling with a Deep Agent

In Step 2 you kept the loop; in Step 3 you wrote the handoff by hand.  **DeepAgents** (`pip install deepagents`), a LangChain-family library built on the *same* LangGraph you just used, takes both of those away and hands you an opinionated harness with four capabilities pre-installed:

- a **planning tool**: the agent writes and revises its own todo list (`write_todos`) as it works;
- **sub-agents**: it can spawn helpers that run in *isolated context windows*, so a research sub-task cannot pollute the main thread;
- a **virtual filesystem**: it offloads long intermediate results to files (`write_file` / `read_file`) instead of carrying them in the prompt;
- a **detailed built-in system prompt**: a long instruction set (modeled on Claude Code) that tells the model *how* to plan, delegate, and use the filesystem.

You supply the tools and the instructions; the loop, the planning, and the delegation are the framework's.  This tutorial builds one up in four small steps; run each cell against the same local Ollama server from Steps 1-3.

> **A note on versions (again):** DeepAgents is young and its API moves: the top-level prompt argument has changed name (`instructions` -> `system_prompt`), a sub-agent's prompt key appears in the docs as both `prompt` and `system_prompt` across releases, and sub-agents can be passed either as these dictionaries or as compiled LangGraph graphs.  The code below is pinned to *conceptual clarity*, not to an exact signature.  If an import or keyword fails, check the current reference at https://docs.langchain.com/oss/python/deepagents/subagents and the README at https://github.com/langchain-ai/deepagents rather than fighting the error.

**Step 4a: the minimal deep agent.**  One call, one tool, no loop.  Notice that you never write a `for` loop or a stopping condition; the harness owns both:

```python

# pip install deepagents   (talks to your local Ollama, same as Steps 1-3)
from deepagents import create_deep_agent
from langchain_core.tools import tool

@tool
def days_between(start_iso: str, end_iso: str) -> str:
    """Returns the number of days between two ISO dates (YYYY-MM-DD)."""
    from datetime import date
    d0, d1 = date.fromisoformat(start_iso), date.fromisoformat(end_iso)
    return str((d1 - d0).days)

agent = create_deep_agent(
    model="ollama:llama3.2",              # same local server as Step 1
    tools=[days_between],                  # YOUR tools, same @tool as Step 2
    system_prompt="You are a scheduling assistant. Plan before you answer.",
)

result = agent.invoke({"messages": "How many days until the final on 2026-12-07, "
                                   "and what should I study each week?"})
print(result["messages"][-1].content)
```

**Step 4b: watch it plan.**  The harness gave the model a `write_todos` tool without you asking.  On a multi-part request the model calls it to lay out a plan, then works the list.  You can see the plan by walking the returned message list instead of only printing the last message:

```python
for m in result["messages"]:
    # planning and tool calls show up as tool-call messages on the AI turns
    for call in getattr(m, "tool_calls", []) or []:
        print(f"[{call['name']}] {call['args']}")

# You will typically see a write_todos(...) call listing the sub-steps the

# agent decided on - a plan you never wrote and cannot see in your own code.
```

**Step 4c: sub-agents with isolated context.**  This is the payoff.  Recall Part II's **Researcher -> Drafter -> Critic** pipeline; there you wired three nodes (LangGraph) or three roles (CrewAI) yourself.  As a deep agent, each becomes a *sub-agent* with its own context window; the main agent decides when to delegate, and each sub-agent's scratch work never touches the others' context:

```python
research_subagent = {
    "name": "researcher",
    "description": "Finds and returns relevant passages for a question. "
                   "Call this when you need sources before writing.",
    "prompt": "You are a rigorous researcher. Return 3-5 passages with sources.",
    "tools": [days_between],   # give sub-agents only the tools they need
}
critic_subagent = {
    "name": "critic",
    "description": "Reviews a draft and returns a bullet list of concrete revisions.",
    "prompt": "You are a demanding editor. List gaps and unsupported claims.",
}

agent = create_deep_agent(
    model="ollama:llama3.2",
    tools=[days_between],
    system_prompt=("You are a study-plan writer. First delegate to `researcher`, "
                   "then draft a plan yourself, then delegate to `critic` and revise."),
    subagents=[research_subagent, critic_subagent],
)

out = agent.invoke({"messages": "Write a 3-week study plan for the final on 2026-12-07."})
print(out["messages"][-1].content)
```

Compare this to Part II's AutoGen `GroupChat`, where **every** agent saw **every** message.  Here the isolation is the default: the critic's private reasoning never lands in the researcher's context, so the cross-talk bug from Critical Thinking Question (CTQ) 5 cannot happen; the framework eliminated a whole class of leak by *construction*.

**Step 4d: the virtual filesystem.**  On long tasks the agent offloads bulky intermediate output to files rather than stuffing it into the prompt.  You can seed files on the way in and read them on the way out through the `files` key of the state:

```python
out = agent.invoke({
    "messages": "Summarize the syllabus notes and save the summary to summary.md.",
    "files": {"syllabus.md": "Week 1: intro...\nWeek 2: agents...\n"},  # seed the FS
})
print(out["files"].get("summary.md", "(no file written)"))   # read what it wrote
```

**Step 4e: choosing the model and provider.**  Every cell above passed `model="ollama:llama3.2"`, but that argument is doing real work worth understanding, because **DeepAgents does not default to a local model**: out of the box it reaches for a hosted Anthropic Claude model and expects that provider's API key.  To run on your own infrastructure you set `model=` explicitly, and it accepts two forms:

```python
from deepagents import create_deep_agent

# Form 1 - a "provider:model" STRING, resolved by LangChain's init_chat_model.

# Requires the matching integration package (here: pip install langchain-ollama).
agent = create_deep_agent(model="ollama:llama3.2", tools=[days_between], system_prompt="...")

# other strings: "openai:gpt-4o-mini", "anthropic:claude-3-5-sonnet-latest", ...

# Form 2 - a fully-constructed chat model OBJECT, when you need to set options

# (base_url, temperature, context length) or point at an OpenAI-compatible server.
from langchain_ollama import ChatOllama
llm = ChatOllama(model="llama3.2", temperature=0, num_ctx=8192)
agent = create_deep_agent(model=llm, tools=[days_between], system_prompt="...")

# To route through OpenWebUI's OpenAI-compatible endpoint instead of Ollama-direct:
from langchain_openai import ChatOpenAI
llm = ChatOpenAI(base_url="http://localhost:3000/api", api_key="sk-...", model="llama3.2")
agent = create_deep_agent(model=llm, tools=[days_between], system_prompt="...")
```

Two things decide whether this works.  First, **the provider must be reachable and its integration installed**: a `provider:model` string only resolves if the corresponding `langchain-<provider>` package is present.  Second, **the model must support tool calling**: DeepAgents' whole architecture (planning, sub-agent delegation) is built out of tool calls, so a model without tool training will stall.  You can also override the model *per sub-agent* (give a sub-agent its own `model` key) so a small, cheap model handles planning while a stronger one drafts, which is often the practical way to keep a deep agent affordable on local hardware.

**Read the whole tutorial against Step 2's ledger.**  There, the framework absorbed only *plumbing* (schema generation, formatting, parsing) while every *decision* (when to stop, what to call, whether a call is safe) stayed in your ten-line loop.  DeepAgents absorbs the decisions too: **when to plan (4b), when to spawn a sub-agent (4c), and what to write to disk (4d)** are now made inside the harness by its built-in system prompt.  That is the opposite trade.  It does a great deal of work for you on long, open-ended tasks, but when the agent plans badly or a sub-agent returns something unexpected, the behavior you must debug lives in the framework's prompt and control flow, not in your code.  Use it once you can describe precisely what it took from you.

# Part V: Hands-On, Pydantic AI and the Context Window

Every framework in this tutorial does one job underneath its abstractions: it builds a context window, sends it to the model, and acts on the reply.  System prompts, memory, skills, tools, and MCP servers look like five different features, but each one reaches the model the same way, as text placed in that window.  This part makes that visible.  You will build a small agent in [Pydantic AI](https://ai.pydantic.dev), a framework from the team behind the Pydantic validation library, add one feature at a time, and print exactly what the model received after each step.

Pydantic AI suits this exercise because it stays close to the raw API.  An `Agent` holds a model, instructions, and tools; `run_sync` runs the same loop you wrote in the Local Agent Lab; and a hook lets you inspect every request before it is sent.  Nothing in this part needs a hosted model: it runs against your local Ollama server.

If you have not met Pydantic AI before, read [Pydantic AI From the Loop Up]({{ site.baseurl }}/Tutorials/PydanticAI) first.  It builds the same kind of agent from the Tool Use deck's `get_today` and `days_until`, and it covers dependencies, permissions, approvals, and testing, which this part leaves out.  The `days_between` tool below is a two-argument cousin of `days_until`, so the traces line up with that tutorial's Part 1.

> **A note on versions:** Pydantic AI moves quickly.  The code below was written for and tested with `pydantic-ai-slim` 2.54.0 and `fastmcp` 4.0.  If an import fails, check the current documentation at https://ai.pydantic.dev before fighting the error message; the ideas (instructions, message history, tools, toolsets, and the agent graph) have stayed stable even as names moved.

## Setup, and a Window Onto the Window

```bash

ollama pull llama3.2               # any local model trained for tool calling will do

```

The `[openai]` extra lets Pydantic AI talk to any OpenAI-compatible server, which includes Ollama's `/v1` endpoint; `[mcp]` brings the MCP client, and `fastmcp` lets you write the small MCP server in Step 5.  Save the helper below as `common.py` next to your scripts.  It does two things.  `make_model()` points Pydantic AI at your local Ollama server, the same server and model as the LangChain section above.  The `watch` hook runs just before every model request and records what is about to be sent, so `show_context()` can print it.  The sample output below comes from a tool-capable model; a reasoning model also prints `[thinking]` entries, which are its own earlier reasoning sent back to it as context.

```python
# common.py: the model, plus a hook that shows exactly what goes into the context window.
import os

from pydantic_ai.capabilities import Hooks
from pydantic_ai.models.openai import OpenAIChatModel
from pydantic_ai.providers.ollama import OllamaProvider

WINDOWS = []  # one entry per model request: (instructions, messages, tools)
watch = Hooks()


@watch.on.before_model_request
async def record(ctx, request_context):
    msgs = request_context.messages
    tools = request_context.model_request_parameters.function_tools
    instructions = getattr(msgs[-1], "instructions", None) if msgs else None
    WINDOWS.append((instructions, list(msgs), list(tools)))
    return request_context


def make_model():
    """llama3.2 on your local Ollama server, through its OpenAI-compatible endpoint."""
    provider = OllamaProvider(base_url=os.environ.get("BASE_URL", "http://localhost:11434/v1"),
                              api_key=os.environ.get("API_KEY"))
    return OpenAIChatModel(os.environ.get("MODEL", "llama3.2"), provider=provider)


def show_context(i=-1):
    """Print everything the model received on request i: instructions, messages, tools."""
    instructions, msgs, tools = WINDOWS[i]
    n = i + 1 if i >= 0 else len(WINDOWS) + i + 1
    print(f"--- request {n} of {len(WINDOWS)}: the context window ---")
    if instructions:
        print(f"[instructions] {instructions!r}")
    for m in msgs:
        for part in m.parts:
            text = str(getattr(part, "content", None) or getattr(part, "args", ""))
            print(f"[{part.part_kind}] {text[:150]!r}{' ...' if len(text) > 150 else ''}")
    for t in tools:
        print(f"[tool offered] {t.name}: {t.description}")
```

To route through OpenWebUI instead, set `BASE_URL=http://localhost:3000/api` and `API_KEY` to your OpenWebUI key before running; nothing else changes.

> **Model choice for tools:** `qwen2.5:3b` (about 1.9 GB, `ollama pull qwen2.5:3b`) is the course's recommended model for tool calling.  It is the same size as `llama3.2` and calls tools far more reliably: in our tests, `llama3.2` sometimes wrote a tool call as plain text instead of making one, or ignored a tool's result in its answer.  `llama3.2` remains fine for plain chat.  `make_model()` reads the `MODEL` environment variable, so `export MODEL=qwen2.5:3b` switches every step without editing code.
{: .tb-tip data-title="qwen2.5:3b for tool calling"}

**Step 2: memory.**  Two kinds of memory, both of them text.  Long-term memory is a file the program reads into the instructions; short-term memory is the earlier conversation, handed back in with `message_history`:

```python
# step2_memory.py
from pathlib import Path
from pydantic_ai import Agent
from common import make_model, show_context, watch

Path("memory.md").write_text("- The student's name is Sam.\n- Sam is taking CS357 and Calculus II.\n")

agent = Agent(make_model(), instructions="You are a concise study-planning assistant.", capabilities=[watch])

@agent.instructions
def long_term_memory() -> str:
    # Long-term memory is a file. Reading it here pastes it into the context.
    return "What you remember about this student:\n" + Path("memory.md").read_text()

first = agent.run_sync("Which two courses am I taking?")
print(first.output)
# Short-term memory: hand the earlier turns back in. Nothing is stored on the server.
second = agent.run_sync("Which of those has more programming?", message_history=first.all_messages())
print(second.output)
show_context()
```

```text
--- request 2 of 2: the context window ---
[instructions] "You are a concise study-planning assistant.\n\nWhat you remember about this student:\n- The student's name is Sam.\n- Sam is taking CS357 and Calculus II."
[user-prompt] 'Which two courses am I taking?'
[text] 'You are taking CS357 and Calculus II.'
[user-prompt] 'Which of those has more programming?'
```

The model answered "which of those" correctly only because the first question and its answer were sent again.  Delete `message_history=...` and run it once more: the second answer falls apart, because nothing on the server remembered the first turn.  Edit `memory.md` and the agent "knows" something new on its next call, with no retraining.  This is the template view of memory from the Memory and Context tutorial, with a framework doing the string-building.

**Step 3: a skill.**  A skill is a prompt the agent brings into its context when it needs it.  Make a `skills/` directory with one folder per skill, each holding a `SKILL.md` like this one (the `citation-check` skill in the code is a second, similar file):

```markdown
---
name: exam-planner
description: Turn an exam date and a topic list into a day-by-day study plan.
---
Count the days until the exam. Give each topic at least one day, put the hardest
topic first, and leave the last day for a full practice exam. Answer as a numbered
list with one line per day.
```

The agent sees a one-line menu of skills on every call and loads a skill's full text only when one fits, which is the same design the terminal coding agents opencode and pi use (see the [Agent CLIs tutorial](https://www.billmongan.com/Ursinus-CS357-Fall2026/Tutorials/AgentCLIs)):

```python
# step3_skill.py
from pathlib import Path
from pydantic_ai import Agent
from common import make_model, show_context, watch

SKILLS = {p.parent.name: p for p in Path("skills").glob("*/SKILL.md")}

def description(path: Path) -> str:
    for line in path.read_text().splitlines():
        if line.startswith("description:"):
            return line.removeprefix("description:").strip()
    return ""

agent = Agent(make_model(), instructions="You are a concise study-planning assistant.", capabilities=[watch])

@agent.instructions
def skill_menu() -> str:
    # Only the one-line descriptions sit in the context until a skill is needed.
    menu = "\n".join(f"- {name}: {description(p)}" for name, p in SKILLS.items())
    return "Skills you can load with load_skill when one fits the task:\n" + menu

@agent.tool_plain
def load_skill(name: str) -> str:
    """Load the full instructions for one skill by name."""
    body = SKILLS[name].read_text().split("---", 2)[2]  # drop the front matter
    return body.strip()

result = agent.run_sync("My calculus exam is in 4 days and covers series, integrals, and limits. Plan my studying.")
print(result.output)
show_context(0)   # first request: the menu only
show_context()    # last request: the skill body has arrived as a tool result
```

Compare the first and last requests of the run:

```text
--- request 1 of 2: the context window ---
[instructions] 'You are a concise study-planning assistant.\n\nSkills you can load with load_skill when one fits the task:\n- citation-check: Check that every factual claim in a draft names a source.\n- exam-planner: Turn an exam date and a topic list into a day-by-day study plan.'
[user-prompt] 'My calculus exam is in 4 days and covers series, integrals, and limits. Plan my studying.'
[tool offered] load_skill: Load the full instructions for one skill by name.
--- request 2 of 2: the context window ---
[instructions] ... (unchanged) ...
[user-prompt] 'My calculus exam is in 4 days and covers series, integrals, and limits. Plan my studying.'
[tool-call] '{"name":"exam-planner"}'
[tool-return] 'Count the days until the exam. Give each topic at least one day, put the hardest\ntopic first, and leave the last day for a full practice exam. ...'
[tool offered] load_skill: Load the full instructions for one skill by name.
```

On the first request, the skill cost one line.  On the second, its whole body sat in the window as a tool result, and the plan the model wrote followed it (hardest topic first, practice exam last).  Pydantic AI has no special "skill" feature, and it did not need one: a decorated function for the menu and a tool that returns file contents were enough.

**Step 4: a tool.**  The same `days_between` tool as the LangChain section, so you can set the two side by side:

**Step 5: MCP.**  Move the tool out of your program and into a server.  This one is a complete MCP server:

```python
# campus_server.py
# campus_server.py: a tiny MCP server. Pydantic AI starts it and talks to it over stdio.
from fastmcp import FastMCP

mcp = FastMCP("campus")

@mcp.tool
def library_hours(day: str) -> str:
    """Opening hours of the campus library for a day of the week, such as Monday or Saturday."""
    return "8am-midnight" if day.lower() not in ("saturday", "sunday") else "10am-6pm"

if __name__ == "__main__":
    mcp.run(show_banner=False)
```

The agent connects to it as a toolset.  Pydantic AI starts the server, asks it what tools it has, and offers them to the model:

```python

from common import make_model, show_context, watch

show_context()
```

```text
--- request 2 of 2: the context window ---
[instructions] 'You are a concise campus assistant.'
[user-prompt] 'When is the library open on Saturday?'
[tool-call] '{"day":"Saturday"}'
[tool-return] '10am-6pm'
[tool offered] library_hours: Opening hours of the campus library for a day of the week, such as Monday or Saturday.
```

The window looks exactly like Step 4's.  MCP changed where the tool lives and how the program discovered it, not what the model sees.  It also means every tool a connected server advertises lands in the window on every call, so a server with thirty tools costs thirty descriptions whether or not the agent uses one.  One more lesson came out of testing this step: an earlier draft of the docstring read "for a weekday name," and the model declined to call the tool for Saturday.  The description is the only thing the model knows about the tool, so it is part of your prompt.

**Step 6: the agentic loop.**  `run_sync` has been running a loop all along.  `agent.iter` lets you walk it one step at a time:

```python
# step6_loop.py
import asyncio
from datetime import date
from pydantic_ai import Agent, UsageLimits
from common import make_model, watch

agent = Agent(make_model(), instructions="You are a concise study-planning assistant. Use tools for date arithmetic.", capabilities=[watch])

@agent.tool_plain
def days_between(start_iso: str, end_iso: str) -> int:
    """Returns the number of days between two ISO dates (YYYY-MM-DD)."""
    return (date.fromisoformat(end_iso) - date.fromisoformat(start_iso)).days

async def main():
    question = "How many days from 2026-10-05 to the 2026-12-14 final, and how many weeks is that?"
    async with agent.iter(question, usage_limits=UsageLimits(request_limit=5)) as run:
        async for node in run:   # one node per step of the loop
            print(type(node).__name__)
    print(run.result.output)

asyncio.run(main())
```

```text
UserPromptNode
ModelRequestNode
CallToolsNode
ModelRequestNode
CallToolsNode
End
There are 70 days from 2026-10-05 to 2026-12-14.

This is exactly 10 weeks.
```

Read the node names against your Local Agent Lab loop.  `ModelRequestNode` is your call to the model with the current context; `CallToolsNode` is your dispatch step, which runs any requested tools and appends their results to the context; `End` is your stopping condition.  `UsageLimits(request_limit=5)` is your step budget: the run stops with an error rather than looping forever.  Each pass through the loop adds the model's reply and any tool results to the window, which is why Step 4's second request carried a tool call and a tool result that its first request did not.

## What Pydantic AI Took Over

Line the six steps up against the from-scratch code you already wrote.  Pydantic AI generated tool schemas from type hints and docstrings, formatted messages for the provider, parsed tool calls, ran the loop, and enforced the budget.  It did not decide what goes into the context: you wrote the instructions, chose what memory to load, designed the skill menu, picked the tools, and chose which MCP servers to connect.  That is the plumbing-versus-decisions line from CTQ 11 again, and it explains why Pydantic AI sits low on this tutorial's abstraction ladder: a CrewAI `Agent(role=...)` writes part of the prompt for you, and a deep agent writes all of it.
